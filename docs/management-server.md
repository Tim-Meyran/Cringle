# ManagementServer

The ManagementServer is the central control instance: CLI and WebUI talk only to it (`proto/cringle/management/v1/management.proto`). It keeps the list of known machines (their Daemons), creates and controls Engines through the Daemons, deploys and controls fabrics through the Engine management API, proxies the Repository and the Router, and answers log queries (fan-out to the running Engines).

Start: `management-server [--home <dir>] [--port <port>] [--repository <host:port>] [--repository-token <token>] [--router <host:port>] [--machine <id>=<daemon host:port>]... [--cache-max-unused-days <n>] [--auth]` (prints `fingerprint=<sha256>` and `management-port=N`). The API of the server is TLS 1.3 with the identity of the server; a client needs no certificate, the user is authenticated by the token, and the CLI pins the fingerprint of the key (`cringle login --fingerprint`, `docs/cli.md`).

State (`<home>/management/state.json`): machines, Engines it created (with `autostart`, default true) and fabrics it deployed (the complete deploy request and whether the fabric should run). This is what recovery uses. The stored request is the one the caller sent, unchanged: if a caller of `DeployFabric` puts a `source.token` (the Repository token) into it, that token is stored in plain text in `state.json`. `Deploy` never does that, and the token the ManagementServer was started with (`--repository-token`) is added only when a request is sent to an Engine and is not stored.

Recovery runs when the server starts (and on demand with `Recover`): Engines with `autostart` are re-registered at their Daemon if needed and started; the fabrics of running Engines are deployed again if the Engine lost them, and started if they should run. A machine that is not reachable is reported in the result, it does not stop the recovery. Stopping a fabric or removing it is remembered; stopping an Engine is not (`autostart` is a setting, not the current state).

With `--auth` the API needs user tokens (user management #22, stored in `<home>/management/users.json`); the very first start prints `bootstrap-token=...` once, a token of the admin user. The same token is also written to `<home>/management/bootstrap-token` (atomically, before the user is stored, with owner-only rights like the CLI profile: `rw-------`, on Windows an access list with the owner only), so it is not lost if the output is: after a crash between storing and printing the token is in the file. The file is deleted at the first successful authentication with that token, which is the first `cringle login`; the token itself keeps working until it is revoked. The ManagementServer then also serves `cringle.user.v1.UserService`, so the CLI needs one address only. Without `--auth` every caller may do everything.

Permissions (user management, #22): `READ` for lists, status, logs and package downloads; `OPERATE` for Engines, fabrics, publishing and `Recover`; `ADMINISTER` for machines, remote routers and plugin trust.

An Engine management API listens on the loopback interface of its machine, so only Engines on the machine of the ManagementServer can be controlled. Placement and download of packages is deployment (#17); `DeployFabric` expects the packages in the Cringle home of the machine.

## Channels and trust

Every channel of the ManagementServer to a Daemon, an Engine, the Repository and a Router is mutual TLS (#7): it presents its identity and accepts a peer only if the fingerprint of its key is in its trust store. Identity and trust store are created at the first start in `<home>/management/certs` and `<home>/management/trust.json` (subject `CN=management:management`). The channel to the ManagementServer itself (CLI, WebUI) is plaintext until #6.

Trust is entered by hand, with fingerprints, on both sides of every link (`cringle trust add` comes with #6; until then the entries are written into the trust files):

| Link | The ManagementServer trusts | The peer trusts |
|---|---|---|
| to a Daemon | the daemon key (`COMPONENT`) | the ManagementServer key (`COMPONENT` in `<home>/daemon/trust.json`) |
| to an Engine | the engine key (`ENGINE`; the daemon knows it, it creates the identity of the engine) | the ManagementServer key, which the Daemon copies from its `COMPONENT` entries into `<engineDir>/trust.json` when it starts the engine |
| to the Repository | the repository key | the ManagementServer key (and every engine key as `ENGINE`, so the engines can download) |
| to a Router | the router key (`ROUTER`) | the ManagementServer key (`COMPONENT`) |

A peer without an entry is refused at the TLS handshake, before any token or permission is looked at (`ManagementTlsTest`). A peer that is removed from a trust store is refused on its next connection; an open connection may run on for at most 60 seconds (`TlsHelper.SESSION_TIMEOUT_SECONDS`).

## Deployment (#17)

`Deploy(project, version_range)` picks the project version (the highest release in the range) and reads the project's fabric configuration. The versions and hashes of the project and its plugins come from the lock `<home>/management/locks/<project>-<version>.lock.json` if there is one for that version (nothing is resolved then, and a package whose hash in the Repository differs from the lock is an error); otherwise they are resolved against the default Repository (issue #6 resolver) and the lock is written. `relock` (CLI: `--relock`) resolves again and overwrites the lock, for example to get a newer compatible plugin release. A lock file that is damaged or inconsistent is an error that names `--relock`; it is never replaced silently. The lock is written atomically (temporary file, then move), so it is either the old or the new file. For each entry it picks `instances` running Engines that have all `roles` and all `labels` (Engines get them with `CreateEngine` or `SetEngineTags`; Engines are never addressed by id), the least loaded first, and sends each Engine a deploy command with the exact plugin versions, their trust status (from the Repository responsible for the Engine's machine; the Engine never asks for it) and the artifacts to download with their hashes. Fabric ids are `<project>-<blueprint>-<n>`. Deploy and `Undeploy` of one project run one after the other (a mutex per project name); other projects are not held up. Deploying a project again replaces its fabrics (stop, remove, deploy: a new version is a restart; blue-green comes later), but only after everything that can fail without touching the running system has worked: resolving or reading the lock, reading the package, placement (every fabric configuration finds enough matching running Engines, counted without the fabrics that are being replaced) and building the deploy commands. If no Engine matches, the error names the requirement and the previous fabrics keep running unchanged. If deploying a fabric fails later, the fabrics that this call deployed are removed and the previous fabrics are deployed again from their recorded requests (and started if they were meant to run); the original error is reported, and it lists the previous fabrics that could not be restored, if any. `Undeploy(project)` removes all fabrics of a project. Where each fabric runs is in the state of the ManagementServer and in the Router registry (the Engines report their fabrics with every heartbeat).

`GetEngine` and `ListEngines` return the status of a running Engine (`status`), which includes its `public_key_fingerprint` (SHA-256 of the public key, the key that other Engines and the ManagementServer trust) and its `tether_port` (0 without tether service) (#172). `cringle engine status` shows the fingerprint. Both are public; they are what a deploy writes into the remote of a bound service tether and into the list of allowed callers of a service.

## Bindings of service dependencies (#171)

A blueprint can name a service of another project instead of a concrete engine (`remote: {"service": ...}`, `spec/package-format.md`). The ManagementServer keeps the bindings of these dependencies, per consumer project and service name: `Bind(consumer_project, service, targets)` binds the pair to one or more fabric ids as `ListFabrics` shows them, in the order of preference (`NOT_FOUND` if no fabric with one of the ids was deployed through this ManagementServer, `INVALID_ARGUMENT` for an empty project, an invalid service name, no target or a fabric named twice); binding again replaces the old binding. `Unbind(consumer_project, service)` removes it (`NOT_FOUND` if there is none), `ListBindings(consumer_project)` lists one project or, if empty, all. The bindings are part of the state file (`management.json`, key `bindings`) and survive a restart; they are per project, not per fabric instance, so they stay when the project is deployed again. `Bind` and `Unbind` need the role operator, `ListBindings` the role viewer. A deploy uses them (#179): for every service tether of a blueprint that the deploy places, the ManagementServer looks up the binding of the project (none: the deploy fails with `FAILED_PRECONDITION` before anything is touched, naming project and service), checks that the target fabric is deployed and provides the service (`provides` of its blueprint), and sends the Engine the fabric, block, port and the key fingerprint of the Engine that runs it as `service_bindings` of the deploy command. A fabric that provides a service gets `service_callers`: the keys of the Engines that run fabrics of the projects bound to it. Fabrics that provide a service are deployed before the others of the same deploy. After a deploy or undeploy of a project the allow-lists (`SetServiceCallers`) of the service fabrics it uses and provides are brought up to date, and the consumers of the service fabrics of the project are deployed again from their recorded requests if the service is now somewhere else. The recorded requests carry the bindings and the allow-list, so `Recover` restores them. Failover (#173): a consumer calls the first target that answers. The deploy sends the other targets as `fallbacks` of the `service_bindings`; the Engine tries them in order, stays on the first one that answers, and while it is on a later one it looks at the better ones every health interval and goes back to the best one that answers again. A change of the list with `Bind` reaches the running fabrics of the project that use the service at once (`UpdateServiceBindings` of the engine API, no redeploy; calls in flight on a connection that is left fail) and updates their recorded requests and the allow-lists of the old and the new targets. If that fails somewhere, `Bind` stores the binding and reports where. `Unbind` removes the consumer from the allow-lists; its running fabrics keep their instances until they are deployed again, but the services no longer accept them.

### Package cache

All Engines that use the same Cringle home share one cache: `<home>/projects/<name>/<version>` and `<home>/plugins/<name>/<version>`. A version is downloaded, its SHA-256 checked against the lock, and unpacked once, in a temporary directory that is moved into place, so a corrupt download (`DATA_LOSS`) or a failed unpack leaves nothing behind. A file lock (and an in-process lock) per version makes Engines that need the same version at the same time wait for each other; installing and cleaning up take the same lock, so neither ever meets a version in the middle of the other. `.cringle-installed` inside a version holds its hash; versions without it were placed by hand and are never touched. Binaries in packages are unpacked with the package and removed with it.

### Cleanup

Each Engine records which package versions its fabrics use (`<home>/cache/usage/<engine>/<fabric>`); the record is removed with the fabric and when the Engine restarts. A version is unused if no fabric of an existing Engine lists it. `CleanupCache(machine, min_unused_seconds)` removes unused versions that were last used at least that long ago (0: all unused; "last used" is when a fabric using it was last deployed or removed). With `--cache-max-unused-days N` the ManagementServer does this for all machines once an hour.

Removing a version is robust against locked files (typically on Windows): the version directory is first renamed in one step to `<version>.removing-<uuid>` and the renamed directory is deleted. If a file in the version is locked, the rename fails, the version stays complete and usable, the other versions are still cleaned up, and the version is reported in `problems` of the result (`<machine>: could not remove <kind>/<name>@<version>: <reason>`). If deleting the renamed directory is interrupted, the version is gone under its name and the rest is a leftover. Leftovers of interrupted work (`*.removing-*` and `*.installing-*` directories next to the versions, `*.part` files in `<home>/cache/downloads`) older than one hour are removed when an Engine starts and by every cleanup; they never count as versions. Whether a version is unused and old enough is decided while holding the lock of that version. A directory without `.cringle-installed` is never a leftover and never touched.

The standard output of an Engine process is read by the Daemon until the process ends. If the log file `<home>/daemon/logs/<engine>.out.log` cannot be written (disk full, file locked), the Daemon reports that once on its error stream and discards the output of that process, so the Engine never blocks on a full pipe.

## Metrics (#191)

`GetMetrics(engine)` returns the numbers of one running engine, or of all running engines (of all machines) if no engine is named (`docs/observability.md`, "Metrics"). An engine that cannot be asked is a line in `problems` and does not fail the call; a stopped or unknown engine that is named is `FAILED_PRECONDITION` or `NOT_FOUND`. The method needs the role viewer. `cringle metrics` shows one row per engine (CPU load, heap, threads, fabrics, errors), `--fabrics` one row per fabric, `--tethers` one row per tether, `--fabric` limits the last two to one fabric, `--json` prints the rows.

## Data warehouse of the engines (#194)

The ManagementServer reads and controls the data warehouse of the engines (`docs/observability.md`). A fabric is named by its id; the
ManagementServer asks the engine it runs on (`NOT_FOUND` for a fabric it does not know, `FAILED_PRECONDITION` if that engine is not
running): `QueryDwh(fabric, kind, name, since, until, limit)` returns the records of a block's or a tether's partition (payload as JSON
text, tags), `ListDwhPartitions(fabric)` the partitions with size and retention (without a fabric: all running engines, an engine that
cannot be asked is a line in `problems`), `SetRecording(fabric, all, default retention)` switches the recording of all typed tethers on or
off, `SetDwhRetention(fabric, kind, name, retention)` sets the retention of a partition. `QueryDwh` and `ListDwhPartitions` need the role
viewer, the other two the role operator. The recording mode is part of the state (`recordings` in `management.json`) and is applied again when
a fabric of that id is deployed again or restored by `Recover`; it is removed when recording is switched off. CLI: `cringle dwh ...`
(`docs/cli.md`).

## Web interface (#207)

With `--web-port <port>` the ManagementServer also serves a web interface over HTTPS (login with the user tokens, sessions, CSRF protection); see [webui.md](webui.md).
